Overview — how this studio works

UI Forge is not another autonomous coding harness. It is a studio for testing UI skills: pick a combination, run the same task with it, compare the rendered result side by side, and rank combinations by fewest defects. Skill sources stay read-only, skill instructions are preserved, and only skills actually read in full count as used.

What changed in Experiment 2

Experiment 1 claimed no live-browser render was possible in this VM. That was wrong: /opt/meta-chromium/chrome is blocked, but the Playwright Chromium binary runs fine over CDP. The parent re-checked all 31 variants at 1280px and 390px — no document horizontal scroll anywhere, 0 console errors, all required text present in the rendered page. Variant 15’s earlier CDP claim, once flagged doubtful, is now confirmed by an independent render. Feel on real hardware is still unverified — headless proves layout, never feel.

Insights — what the experiments actually showed

Provisional ranking, single run except the three repeats. Ranked on defects left known (0 for 30 of 31), thoroughness of checking, accessibility work, working interaction, conflict-resolution quality, and repeat consistency — not on rendered visual feel, which was measured only for scroll, console errors, and text presence.

Defects found + fixed per variant

“Found + fixed” measures checking thoroughness as much as combo quality — a builder that checked harder finds more. Gold bars are the top five.

Repeat consistency — did the win reproduce?

  • Typography → Layout (02 → 12): run 1 found 0 real defects; run 2 found 4 items (2 fixes + 2 pre-build changes) and 1 deliberate known-left (flat bars). Quality held; the count did not reproduce.
  • pstack+ecc+custom (04 → 13): run 1 found 7; run 2 found 1 — but resolved the same 2 conflicts identically (press 0.96, stagger 100ms). The repeat draft was cleaner; run 1’s “7” looks like builder thoroughness, not combo quality.
  • PanelUI web (07 → 14): 4 → 5, same defect classes (chart baseline, table/stat at 390px). Most reproducible repeat.
  • Lesson: ranking order held for all three repeats, but defect counts are builder-dependent. Future rankings should average 2–3 builders per combo.

Order effect — Typography → Layout vs Layout → Typography

  • 02 (Typography → Layout): 0 real defects.
  • 11 (Layout → Typography): 5 fixed, including 1 HIGH — mobile search never displayed, a base CSS rule overriding a media query by cascade order.
  • Verdict: inconclusive. 11 found more, but builders differ and the HIGH defect is a plain cascade-order mistake no skill-order rule predicts. Builder variance dominates; a real order test needs the same builder (or several per order).

Conflict findings — two design systems, one page

  • 26 Astryx + OpenSourceUI — 12 conflicts. Radius: Astryx 12/10/6 beat OSUI 16px. Elevation: OSUI flat won — the frosted-glass notification banner was flattened, the most visible casualty.
  • 27 PanelUI + Astryx — 9 conflicts. One merged token layer (--ax-* values, --pui-* roles). Radii: shadcn scale won. Charts: PanelUI BarChart won (Astryx charts are @canary-only).
  • 30 full UI stack — 10 conflicts. Press 0.96, stagger 100ms, easing split by use; Astryx values on PanelUI semantic names. Still shipped with 0 defects left.
  • Lesson: merges work, but every one costs a named decision and at least one visible casualty. No variant failed to build; no conflict was unresolvable.

What worked

  • Process beats any single skill: pstack + ECC + custom (04/13) tops the ranking — the rigour (prove-it-works, checklists) caught what design systems alone did not.
  • One strong component system is enough: PanelUI web alone (07/14) is #3/#4 — NavRail, KPI, BarChart, Table, Frame as a complete kit.
  • Single atomic skills are measurable: layout alone (08) and colors alone (09) each fixed real, specific defects — 2 and 3 — proving the singles do visible work.
  • Accessibility-only is not a side quest: variant 20 fixed 3 real a11y defects (outline removal, visual-only chart, pointer-only scroll) that no other single skill caught.
  • “Everything” is viable, not magical: the full stack (30) ranks #5 — good, but not better than the focused 04 combo, and it cost 10 recorded decisions.

Honest limits

Layout, horizontal scroll, console errors and rendered text are measured (headless Chromium 156, all 31 variants, 1280px and 390px). Visual feel, taste, touch behaviour, screen readers, and Safari/Firefox are not — no variant was eyeballed on real hardware. One run per variant except the three repeats, and defect counts did not reproduce across repeats. Astryx, OpenSourceUI and PanelUI were adapted to single-file HTML, not real React / Expo builds. This ranking is provisional until repeated — see experiments/RESULTS.md for the full method.
